# Memory System

Loa uses several distinct kinds of persisted and active state. They should not be collapsed into one generic "memory" bucket, because they have different lifetimes and are used differently by the engine.

The current implementation also deliberately avoids using recursive whole-context summarization as the mechanism for fitting long tasks into a model context window. Original task/tool state remains persisted; each model request receives a newly composed subset of the state that is relevant to that inference.

## 1. Project Memory

**Path:** `.loa/project_memory.json`

Project memory is a persistent `memory.Store` for the project. It contains memory items and task summaries, including structural memories (`MemoryStructural`) generated by the crawler.

Structural memories are anchored to project-relative file paths and store a CRC32 `file_hash` of the indexed file content. This enables accurate reconciliation: when a file is created, modified, or deleted, Loa removes outdated memories anchored to that path and regenerates the structural representation from the current file on disk.

### Structural Crawl & Reconciliation Triggers

The project index (`internal/index`) tracks all non-ignored UTF-8 text files in the repository—both source files with Universal Ctags AST symbols and symbol-less text/documentation/config files (such as `.txt` files or `.md` files without headings), while excluding built-in ignored directories/files, `.loaignore` matches, and binary files.

The crawler (`RunCrawler`) inspects all indexed files that do not yet have a current `MemoryStructural` item in `project_memory.json` (skipping empty or whitespace-only files). For each chunk of an unindexed file it performs:

1. `NarrativeFrame` inference over the source/text chunk,
2. `ExtractKeywords` inference over the resulting frame,
3. vector embedding generation,
4. persistence of a `MemoryStructural` item anchored to the file path with its CRC32 `file_hash`.

Files smaller than `crawler_small_file_threshold` lines—or files with zero ctags symbols—are processed as a single whole-file chunk. Larger files with ctags symbols are split into logical chunks along symbol boundaries using `crawler_max_chunk_lines`.

Stale or newly discovered files are crawled at four points in Loa's lifecycle:

- **Boot Scan:** at startup or initial project setup, verifying all indexed files and CRC32 hashes against `project_memory.json`.
- **Idle Watcher Auto-Crawl:** when `fsnotify` detects disk changes and Loa is currently idle (`!running`), stale files are immediately repaired and crawled after the `fs_watcher_debounce_ms` window without waiting for the next user message.
- **Just-In-Time Pre-Retrieval:** while a task is running, file edits (via agent tools or disk events) lazily mark files stale without pausing execution on every intermediate write; if the agent triggers a memory retrieval (`retrieveMemoryRound`), pending stale files are flushed and crawled first so search results are fresh.
- **Task Finalization:** when a Planned or Fast task completes (`finishTask` / `fast_complete`), any remaining stale files accumulated during the run are flushed in a single batch crawl.

Because Narrative Frame and keyword generation are model calls, an initial project crawl can issue many inferences before the user starts a normal coding task.

## 2. Session Memory

**Path:** `.loa/sessions/<session_id>_memory.json`

Each active session can have its own `memory.Store`. Session memory uses the session-specific decay/weight configuration and stores session-scoped retrievable information and task summaries.

At task finalization, Loa runs `SummarizeTask`. The resulting task summary is keyworded/embedded and is stored in the session memory store when that store is available. The engine can also run `ConsolidateContext` to derive reusable semantic facts or architectural decisions from the completed task context.

These derived memories are retrieval aids. They do not replace the persisted original tool/task records.

## 3. Persisted Session State

**Path:** `.loa/sessions/<session_id>.json`

This is separate from the session memory store.

Persisted session state contains the operational state required to continue and inspect a conversation/task: messages, the active task/DAG, tool calls/results, execution records, and related state managed by the state store.

On reload, an active task that was persisted as `running` is converted to `paused` so it can be resumed safely rather than appearing to continue inside a process that no longer exists.

## 4. Active Task Context / Working Memory

The UI's **Working Memory** view corresponds to information held in the active task state: current facts, decisions, constraints, open issues, guidance, and related task context used while the task is running. The `TaskState` also explicitly tracks a synthesized `Target` to focus the agent on specific operational target components or entities.

At normal Planned step completion, `RefreshTaskContext` rebuilds that structured task context from the prior task context, the newly completed `StepResult`, and the task's acceptance criteria. If that model operation fails, the engine has a deterministic fallback that carries forward extracted facts/decisions.

This is structured task-state consolidation. It should not be confused with recursively replacing the underlying source/tool evidence with ever-smaller summaries.

## 5. Context Reconstruction

Every model inference receives a freshly assembled context from `internal/agent/context.go`.

The current builder starts with mandatory task information such as:

- current time/project root,
- persistent project instructions,
- pending clarification state,
- active task state and acceptance criteria,
- current step,
- direct prerequisite step results,
- recent step-result breadcrumbs,
- user guidance,
- active attachment paths and permissions.

It then adds recent conversation messages and extra retrieved/tool context subject to the configured limits.

### Direct DAG Prerequisites

For a current plan step, Loa injects completed `StepResult` values only from that step's direct `depends_on` dependencies as direct prerequisites.

This is why DAG edges are also context topology: changing a dependency can change which prior results are routed into a later inference.

### Recent Breadcrumbs

`context_recent_breadcrumbs` controls a tail of compact completed-step result summaries that can be added alongside the direct prerequisites.

### Chat History

The context builder does not inject chat history into prompts. Agents pull it with the `read_history` action (available in step execution and in the pre-planning research loop): `offset` 0 is the newest message, `count` is optional and capped by `recent_messages`. The requested messages are consolidated against the agent's stated reason, and only that consolidated result is added as extra context. `ResolveAmbiguity` is the one exception: it receives the last 3 messages through its own input.

### Extra Context

Retrieved memory/tool context is added from the newest entries backward. It is bounded both by remaining prompt space and by `code_budget`.

If a piece does not fit, it can be truncated to the remaining available runes. The builder does not invoke a model to recursively summarize the entire previous prompt just to make it fit.

## 6. Token Budget Semantics

`context_budget` is a **per-inference context limit**, not a total task token/inference budget.

The current builder estimates prompt size using an approximate rune-to-token conversion. It reserves:

- a safety buffer (dynamically calculated using `context_prompt_margin_percent` and `context_network_margin_percent` against `context_budget`),
- `output_reserve` for model output,
- any immutable overhead required for the current inference (such as the dynamically calculated cost of a JSON repair stack trace).

The resulting prompt allowance represents the available `slackRunes` for Extra Context (retrieved memories, tool outputs, and on-demand consolidated history reads). `code_budget` limits the maximum amount of extra material that can be injected, while dynamic squashing ensures that large, unavoidable overheads (like JSON repair loops) smoothly compress the available extra context rather than blowing past the context window.

This means a task can remain within its configured context budget on every individual inference while still making hundreds of model requests over the lifetime of the task.

## 7. Decay and Retrieval

Project/session memory decay settings affect retrieval scoring. They do not mean that Loa periodically rewrites memories into compressed summaries or deletes them at a fixed half-life.

The memory store applies the configured half-life/max-weight values when scoring search results. Retrieval can also use a candidate pool and reranking passes before returning memories to the engine.

## 8. Original Evidence vs. Derived Memory

Loa does generate derived representations in specific places:

- Narrative Frames for code chunks,
- extracted keywords,
- structured `StepResult` values,
- refreshed task context,
- task summaries,
- consolidated semantic memories,
- explicit `analyze_large_file` summaries when that tool is used.

These mechanisms should not be described as one generic "context compression" pipeline. The active context builder does not repeatedly replace the entire history with a compressed model-written version. Persisted task/tool/source state remains available separately, while the engine selects and routes the material needed for each inference.

## 9. Local vs. Remote Processing

The memory/state files described above are stored locally inside the project/runtime directories.

That does **not** by itself mean every operation is offline. Narrative Frames, keyword extraction, planning, execution and other primitives are sent to the configured model endpoint. Embeddings can either use Loa's local GGUF embedding engine or the configured OpenAI-compatible embedding endpoint.

Loa is fully local only when the configured inference and embedding paths are also local/self-hosted.
